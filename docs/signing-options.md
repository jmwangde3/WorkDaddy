# 代码签名选择（1.3.1 结论）

> 本文只做选择分析，不代表已经购买或已经签名。当前发布资产**未签名**。
> 证书产品与资格要求会变，签约前以各 CA / 平台官方条款为准。

## 1. 现状：未签名发布意味着什么

| 影响 | 说明 |
| --- | --- |
| SmartScreen 警告 | 用户双击 Setup / 便携版 EXE 时出现「Windows 已保护你的电脑 → 未知发布者」。要点「更多信息 → 仍要运行」才能继续 |
| 声誉 | 未签名 + 下载量小的新文件更容易被判为可疑；文件名/哈希每次发布都变，声誉不会累积 |
| 企业环境 | 部分受管设备直接禁止运行未签名安装包（AppLocker / WDAC / Smart App Control） |
| 来源证明 | 无法证明「这个 exe 由本仓库构建」。别人可以重新打包并声称是同一版本 |
| 时间戳 | 无签名就没有可信时间戳，无法证明某版本何时存在过 |

对当前阶段（个人 fork、少量用户、AGPL-3.0 源码公开）的影响主要是第一条：
用户会看到一次警告，且这个警告**不会**因为提供了 SHA256SUMS 而消失。

## 2. 可用的 Authenticode 方式

### 2.1 OV 代码签名证书

- 形式：CA 签发的代码签名证书（Sectigo / DigiCert / GlobalSign 等），私钥在 USB token 或云 HSM。
- 价格量级：每年数百到一千多元人民币。
- SmartScreen：**不会立即信任**。需要下载量/时间累积声誉；新证书前期仍可能报警。
- CI 集成：token 无法直接给 GitHub hosted runner 用；要么自建 runner 插 token，要么用 CA 的云签名服务。

### 2.2 EV 代码签名证书

- 形式：硬件 token，私钥不可导出，CA 做更严格的主体核验。
- SmartScreen：历史上 EV 能立即建立信任；近年微软也引入声誉机制，但 EV 仍是最快见效的一档。
- 成本与流程：比 OV 贵、核验更严、必须有实体主体（个人也可申请，但材料更多）。
- CI：同样受 token 限制，通常配合自建 runner 或云签名。

### 2.3 云签名服务（推荐给 CI）

- **Azure Trusted Signing**（原 Azure Code Signing）：微软托管密钥，官方 GitHub Action，按签名次数/月订阅计费；需要主体资格审核（组织通常要求一定经营年限）。
- **SignPath.io / SignPath Foundation**：面向开源项目的签名服务，AGPL-3.0 这类许可证通常符合 Foundation 的免费条件；提供 GitHub Actions 集成与人工审批门。
- 共同优点：私钥不落 CI，签名动作可审计，适合 release.yml 这种 tag 触发的流程。
- 共同前提：需要项目主体通过审核，申请有等待期。

### 2.4 自签名证书

- 做法：`New-SelfSignedCertificate` 生成代码签名证书，`signtool sign /f cert.pfx`。
- 适用范围：**只适合自己机器或内部测试**。要在别的机器上生效，必须先手动把根证书导入「受信任的根证书颁发机构」。
- 对公众发布：比未签名**更糟** —— 用户仍会看到警告，而且「已签名但不受信任」容易被误判为异常文件。
- **不能**把自签名描述成「已获得 SmartScreen 信任」。自签名与 SmartScreen 声誉系统没有任何关系。

## 3. 正式发布需要的最小要求

1. 私钥永不进入仓库、日志、Artifact；`*.pfx` 加进 `.gitignore` 并视为事故级泄露。
2. CI 用 OIDC / 云 KMS 或托管签名服务；`GITHUB_TOKEN` 权限按 job 最小化（当前 `release.yml` 已是 `contents: write` 单点）。
3. 签名放在独立 job，且在「资产校验通过」之后执行；签名后再重算 `SHA256SUMS.txt`。
4. 必须带 RFC 3161 时间戳（`/tr` + `/td sha256`），否则证书过期后旧版本签名失效。
5. 签名后校验：`signtool verify /pa /all` 必须通过，并把结果写进发布报告。
6. 证书过期/吊销的应对：保留上一版可用资产，不在原 Release 上覆盖（当前流程默认拒绝覆盖）。

## 4. SHA256SUMS 能保证什么、不能保证什么

**能保证**

- 下载到的文件与清单里那一条逐字节一致：传输损坏、镜像同步不全、单个文件被替换都能发现。
- 用户可以离线核对：`sha256sum -c SHA256SUMS.txt`（清单是 LF 行尾，就是为这个准备的）。
- 与源码包配合时，能证明「这个 zip 就是这次构建产出的那一份」，而不是别的构建。

**不能保证**

- **发布者身份**：清单和资产放在同一个 Release 里，能改资产的人也能改清单。没有签名时，SHA256 只是完整性校验，不是身份校验。
- 不会消除 SmartScreen 警告，也不会让 Windows 显示发布者名称。
- 不能防止「有人另建一个仓库/网盘页面，放一份他自己的资产和配套清单」。

结论：SHA256SUMS 是**必要的**，但对「用户敢不敢双击」这个问题帮助有限。要解决那一步只能靠 Authenticode 签名 + 声誉。

## 5. 本轮建议

1. **1.3.1 继续未签名发布**，但在 Release 说明里写清：未签名、如何核对 SHA256、如何从源码自行构建。
2. 不购买证书、不生成自签名证书，也不把自签名包发给外部用户。
3. 若后续要正式对外分发，优先评估 **SignPath Foundation（开源免费）**，其次 **Azure Trusted Signing**；两者都不需要把私钥交给 CI。
4. 在此之前，降低风险的实际手段是：发布资产只从 tag 构建（已强制）、SHA256SUMS 全覆盖并逐条重算（已强制）、Release 默认拒绝覆盖（已强制）。
